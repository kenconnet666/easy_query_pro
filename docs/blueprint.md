# EasyQuery Pro 完整交付蓝图

状态：完整目标的规划提案，待范围确认后用于无人值守实施。阶段表示依赖顺序，不表示可以在中途把项目宣布为完成。

目标是交付一个基于 EasyQuery 3.2.17、使用 Java 17、面向 MySQL、PostgreSQL 和 SAP HANA 的成熟增强包。HANA 适配是核心交付；通用查询继续沿用 EasyQuery，确有差异的数据库类型和操作通过显式、可组合的 DSL 表达。完成条件包括功能、错误行为、类型安全、实际数据库验证、应用接入、性能证据、文档和可消费产物。

公开 API 的分层、通用新增清单、三库类型目录与逐领域方言实现，详见 [通用 DSL 核心与数据库方言设计](dsl-design.md)。该文档细化本蓝图的能力归属，避免把全部功能都放进通用核心或全部复制成方言方法。

## 1 完成后的使用体验

项目必须同时满足以下使用场景，不能只以某个示例能运行作为完成依据。

1. 普通 Java 应用引入 HANA 模块并选择 `HanaDatabaseConfiguration`，使用既有 EasyQuery API 完成订单、明细、库存等实体的查询、关联、分页、写入、主键回填和事务。
2. 同一组通用业务查询能分别在三库执行。差异由适配器处理；不能要求业务层为普通日期、字符串、金额运算到处判断数据库。
3. 需要精确 SQL 类型、JSON、数组、全文检索时，使用者可以明确选择类型和方言入口，仍能把结果组合进原有 select、where、orderBy、groupBy 和子查询。
4. HANA 应用能够查询普通视图、带输入参数的计算视图和选定的表函数，能够处理组织结构等层级数据；这些能力有真实 HANA fixture，不以字符串快照代替执行验证。
5. 应用能够生成和检查受支持的 Code First 命令，了解既有 schema、表、列、主键和索引。没有被支持的迁移操作会在执行前明确失败，不会误用其他数据库的默认 SQL。
6. 使用者可以从发行 JAR、README、示例和兼容表独立接入。遇到错库、无效类型参数、不支持的能力或驱动异常时，能够定位原因。
7. 维护者可以在干净环境运行 CI、重现问题、升级受控依赖并验证回归。发布结论绑定具体 commit、产物和测试矩阵。

“成熟可用”以本蓝图中的完整范围和完成条件为准。基础 CRUD、容器健康、原生 JDBC 连通或单库冒烟都只是中间证据。

## 3 已有能力必须复用

以下结论来自 3.2.17 本地代码；实现前还要落实为逐方法的能力清单。

| 能力 | 上游入口 | 处理原则 |
| --- | --- | --- |
| 数据库安装 | `DatabaseConfiguration`、`ServiceCollection` | HANA 走同一安装机制，不建立第二套容器 |
| SQL 生成 | `SQLKeyword`、`ExpressionFactory`、现有 expression 与 segment | 只替换数据库差异，保留上游参数和表访问模型 |
| 通用函数 | `SQLFunc` 及字符串、时间、数字、聚合、JSON 子接口 | 补 HANA 翻译；已有方法不换名字重新包装一套 |
| JDBC 类型 | `JdbcTypeHandler`、`JdbcTypeHandlerManager`、`@Column.jdbcType/typeHandler` | 复用绑定和读取机制，按 client 隔离注册 |
| 值转换 | `ValueConverter`、`ColumnValueSQLConverter` | 保持 Java 值转换与 SQL 转换的职责，不重做序列化框架 |
| JSON | `SQLJsonFunc` 已有字段、key、数组取值和长度接口 | 先完成通用契约，再补真实缺失的操作 |
| 窗口 | 排名、聚合、LAG/LEAD、FIRST/LAST/NTH_VALUE 已有实现 | 扩展窗口 frame 和组合边界，不重复发明上述函数 |
| 条件聚合 | Proxy `.filter(...)` 已可通过 CASE 表达 | 不把“没有原生 FILTER 语法”误判为功能缺失 |
| 冲突写入 | `onConflictThen` 与既有插入行为 | 翻译既有语义，不增加另一套通用 upsert API |
| CTE 与树 | 普通 CTE、`CTERecursiveProvider` 和树查询 | HANA 普通 CTE 适配；树语义与 HIERARCHY 对接；任意递归 CTE 单独界定 |
| 迁移 | `DatabaseMigrationProvider`、`MigrationEntityParser`、Code First 命令 | 复用契约，补 HANA 元数据与 DDL |
| 业务扩展 | 导航属性、过滤器、逻辑删除、拦截器、转换器、分片等 | 验证兼容，不重复实现其框架 |
| Spring 配置 | `StarterConfigurer` 在 starter 的数据库配置之后调用，已有 `SQL92` 选项 | 优先验证现有钩子和显式 Bean，不先创建新 starter |

特别注意：3.2.17 已调整 LIKE 转义；APT 的 Java 属性到 DSL 列映射仍为固定映射；源码中完全注释掉的 `AbstractSQLColumnProxy` 等类不能作为可用 SPI。SQL 生成和 JDBC 执行是不同层，单条语句语法正确不代表主键、批处理和事务契约成立。

### 为什么选择这些能力

| 决定 | 价值与取舍依据 |
| --- | --- |
| HANA 普通能力先完整接入 | 上游缺少这个数据库后端，价值最高；复用现有查询 API 能让大量既有业务直接受益，避免同时改变数据库和业务写法 |
| 主键、批量、事务和 LOB 作为硬要求 | 这些决定真实应用能否可靠写入和处理数据；只有 SELECT 能跑的适配不能支撑成熟使用 |
| 加入计算视图、表函数和层级 | 它们与 SAP HANA 的实际使用密切相关，是数据库专项能力的合理投入；不因此扩展到 ABAP/RFC 或 SAP 业务框架 |
| 精确类型与 CAST 独立建模 | Java Class 不能完整描述长度、精度和原生类型；精确类型能增加能力，同时保留普通实体和通用调用 |
| JSON、PG 数组和全文纳入完整目标 | 这些能力在目标数据库中有明确操作和索引语义，可减少业务层手写 SQL；用方言入口表达差异比伪造统一语义更可靠 |
| 窗口重点补 frame 和组合 | 排名和偏移等基础函数已存在，新增价值在累计、区间分析和 peer group 的准确语义，而不是重新命名已有函数 |
| Code First 与应用接入一并完成 | 查询、类型与 DDL 不一致会把问题推给使用者；成熟交付需要正确元数据、可审阅迁移和可运行消费者 |
| 正确性之后继续做性能、文档和产物验收 | 无人值守执行必须覆盖实际交付成本，不能在内部测试通过时把剩余工作交回给用户 |

若某项审计发现上游已经完整实现，交付方式应改为复用、兼容测试和说明，不再新增同等实现。该能力 ID 仍保留并按同样标准验收，这属于正确复用，不属于删减范围。

## 5 明确不纳入的能力及理由

| 不纳入内容 | 取舍理由 |
| --- | --- |
| 其他数据库、HANA Cloud 的兼容承诺 | 用户已限定三库；未验证版本和产品不能扩大承诺 |
| 新 ORM 执行器、查询 AST、通用 Queryable 副本 | EasyQuery 已有模型，复制会造成表达式与执行契约长期分叉 |
| 复制或 fork APT/KSP、全查询链增加数据库泛型 | 影响面远超增强边界；显式类型视图可以先实现目标，需要上游 SPI 时单独处理阻塞 |
| 重做导航、多租户、分库分表、缓存、审计和加密框架 | 已有机制应验证兼容；跨不同数据库的一条分布式查询不在目标内 |
| 一次覆盖数据库全部原生函数、空间/图/向量引擎 | 无确定需求且需要独立数据模型、索引和执行契约，不能靠堆方法名形成成熟度 |
| 通用跨库 RETURNING、存储过程语言或 SQLScript 开发框架 | 涉及多结果集和执行协议的新体系；当前交付集中在查询与类型增强 |
| 自动升级生产数据库或 SAP 自带业务表 | 迁移命令支持不等于拥有任意数据库变更权限；本包不自动改外部业务资产 |
| 通用搜索相关性分数、无条件客户端计算降级 | 各库语义不同；静默下载数据改变过滤、排序、分页和性能契约 |

这里列出的不纳入项是产品职责边界。第 4 节的必交付项遇到困难时不能移入本表来获得完成状态。

## 6 模块与扩展边界

保留现有五个生产模块。`easy-query-pro-hana` 只依赖 `sql-core`，包含数据库配置、表达式、通用函数、类型处理和迁移。`easy-query-pro-dsl` 依赖 `sql-api-proxy`，只承载确有共同语义的扩展和必要互操作代码。三个方言 DSL 模块承载各自类型、JSON/数组/全文等专属操作。

MySQL/PG 的适配器继续使用上游实现；需要安装增强服务时采用薄的配置组合，不复制数据库后端。HANA 的身份和能力由其安装入口注册；MySQL/PG 的增强安装入口同样注册到当前 runtime。不能根据引号样式、字段 Java 类型或全局静态变量猜测数据库。

生产模块不强制带入 Spring、连接池、JSON 序列化库和所有 JDBC 驱动。绑定行为如确需驱动专属类，优先用标准 JDBC；确实无法避免时只对相应模块使用明确的可选依赖，并验证驱动缺失时的错误。

新增通用 DSL 的契约和小型函数工厂接口放在通用模块，MySQL/PG/HANA 实现分别放在对应 `dsl-*` 模块。HANA 底层适配器只处理上游契约，不反向依赖 Proxy DSL；原有 SQLFunc 与新增操作工厂分别管理，避免完整转发或替换整套原有服务。

目录按 `config`、`expression`、`function`、`type`、`migration` 等真实职责建立。测试按 `sql`、`contract`、`hana`、`mysql`、`pgsql`、`consumer` 分组。可运行示例放入独立消费工程，不发布测试库。没有实际重复和调用收益时，不增加 `core`、`spi`、注册中心或泛化插件框架。

## 7 类型化 DSL 的具体设计约束

必须分别处理 Java 业务值、SQL 存储类型、JDBC 绑定，以及表达式可用操作。一个 String 属性可能是普通文本、JSON 或长文本，不能全局替换成某个数据库专属列；标准实体仍保持普通 Java 类型。

通用类型用于可移植需求，方言类型用于真实差异。以下是使用意图，方法名可在原型期按 Java 类型推导与上游命名调整；完整交付必须提供同等能力，不能以伪代码作为实现：

```java
// Existing common queries remain unchanged.
order.name().contains(keyword);

// Proposed precise, portable conversion.
ProDsl.of(order).cast(order.amount(), CommonTypes.decimal(19, 4));

// Proposed explicit dialect operations.
HanaDsl.of(order).cast(order.name(), HanaTypes.nvarchar(200));
MySqlDsl.of(order).json(order.attributes()).containsJson(jsonText);
PgSqlDsl.of(order).jsonb(order.attributes()).containsJson(jsonText);
```

设计必须满足：

- `cast` 产生真实 SQL 转换和新表达式；`jsonb(...)` 等列视图表示已有存储/操作意图，不能偷偷改变原列的 Java 元数据或把视图当作 CAST。
- DDL 类型名和 CAST 目标分别渲染。MySQL 的字符 CAST 语法应按其官方规则处理，不能把 `VARCHAR(n)` 等 DDL 字符串直接拼进去。[MySQL CAST](https://dev.mysql.com/doc/refman/8.4/en/cast-functions.html)
- 返回字符串、数字、布尔、日期或专属 JSON/数组表达式时，保留相应操作的静态类型，不能全部退化成 Object 或要求调用者强转。
- 方言类型在相应方法签名中受约束；同时检查 runtime 方言和表达式上下文。上游查询链没有数据库泛型，不能宣称所有错库组合均在编译期被发现。
- 上下文合法性遵循同一查询树和相关子查询规则，不能简单用上下文对象是否相同拒绝合法的多表、别名或相关子查询。
- 参数类型错误、PG 类型传入 HANA 方法等提供编译负例；跨 client、跨方言表达式混用提供运行时负例。
- 复用 `PropTypeColumn`、`SQLFunction`、现有 selector/segment 和绑定机制；保留表访问、别名、聚合类型及参数顺序，不解析生成 SQL 再做字符串替换。
- 类型长度、precision/scale、窗口边界等结构参数做边界校验。数据值优先绑定；必须是 SQL 语法字面量的部分由受控节点渲染。
- JSON 实体序列化复用上游转换器。JSON 文本可以作为绑定值，不为此强制引入 Jackson，也不再写一套 JSON 解析器。
- 仅在三个真实方言实现证明需要后提取共同类型契约。Java 17 的 record 用于不可变描述，sealed 仅用于明确封闭的内部节点；用户扩展点保持可扩展。

如果现有公开 SPI 无法保留必需的表达式语义，必须提交最小可复现案例和所需 SPI 变化说明。不能依赖反射修改私有字段、覆写上游同包类、动态补丁或复制整个 Proxy 生成器。

## 8 HANA SQL 与类型实现

### 8.1 查询和执行

从 `HanaDatabaseConfiguration` 注册 `SQLKeyword`、`ExpressionFactory`、`SQLFunc`、必要的 JDBC handler 和迁移实现。先验证可直接复用的 ANSI 行为，再覆盖 HANA 差异，避免不加区分继承默认函数。

查询覆盖 schema、双引号、大小写、保留字、派生表、普通视图、子查询、JOIN、聚合、分页与普通 CTE。分页测试包含重复排序值、空结果、边界 offset、count 与 group/distinct 组合。NULL 排序和未指定排序的行为必须写入契约，不能暗示无 ORDER BY 的稳定分页。

写入覆盖默认列、全默认插入、NULL 策略、批量参数、选择更新列与安全删除开关。identity 和 sequence 回填必须尽早验证：上游实际通过带列名的 `prepareStatement` 和 `getGeneratedKeys()` 回填，不是仅渲染 INSERT。必要适配必须保留当前事务连接和输入顺序。

冲突写入先固定既有 API 的插入、忽略、指定字段更新、复合键和行数语义，再验证 HANA 对应实现。并发失败不能吞成成功；不能用先 SELECT 再 INSERT/UPDATE 代替原子操作。数据库受影响行数确有差异时明确说明，不伪造统一数值。

### 8.2 类型契约

| 类型族 | 完整要求 |
| --- | --- |
| 整数和布尔 | Java signed 范围、primitive/wrapper、NULL 与 false/0 区分；不能按类型名字相似直接映射 |
| decimal 和浮点 | precision/scale、舍入、溢出、正负边界；金额不经 Double 中转；浮点异常值按数据库实际能力处理 |
| 字符和二进制 | Unicode、组合字符、空串、长度边界、byte[]；标识符与数据值分别转义 |
| 日期时间 | LocalDate/LocalTime/LocalDateTime 的本地语义、数据库精度、日期边界、闰年和月末；不得用 JVM 默认时区偷偷改变值 |
| 时间点 | Instant 采用明确 UTC 契约并验证三库读写；需要保留原始 offset 的值不能无声明地压入不带时区的列，要求明确映射方案 |
| UUID | 复用上游已有 handler；HANA 明确缺省存储方案；文本与二进制 UUID 的选择和字节顺序不能隐式混用 |
| LOB | NCLOB/CLOB/BLOB 的空值、大值、流生命周期、批处理和结果读取；不把所有长数据无条件提前加载 |
| JSON/PG 数组 | SQL NULL 与内容值分离，完整绑定和读取；结果投影与实体转换器都要验证 |

### 8.3 通用函数清单

需要建立逐操作清单，而不是只列函数类别：字符串拼接/大小写/裁剪/子串/索引/补齐/LIKE，NULL/default/CASE，数学与数值计算，日期提取/格式化/加减/间隔，聚合与条件聚合，JSON，已有窗口函数及 CAST。

每项记录原有入口、语义、HANA 渲染、参数规则、直接复用或覆盖的依据，以及测试位置。测试必须包含 NULL、边界和嵌套。特别关注索引从 0 还是 1 开始、LIKE 通配符转义、月份加减、时间差方向、空聚合、bool 投影与条件表达式的区别。

所有暴露入口都要归类。必交付核心操作不能留成未验证的默认继承；确有数据库限制的非适用变体必须在支持表中给出精确条件与执行前拒绝行为。

## 9 元数据与迁移

完整范围包含 table/view 识别、schema/列/主键/索引/外键/注释/默认值/identity 的查询，创建 COLUMN TABLE、基本行存表的查询写入兼容，以及普通索引、主外键和列定义的生成。

增量迁移覆盖新增列、索引与约束，受支持的扩宽、注释/default/nullability 变更以及明确的重命名命令。删除、缩窄和可能丢数据的变更必须进入显式命令审阅流程，不作为自动同步的默认动作。创建数据库租户、实例管理和 SAP 产品 schema 升级不属于普通 Code First。

执行顺序遵循上游命令模型。必须验证：已存在对象的幂等行为，跨 schema 同名对象，权限不足与对象不存在的区别，中途失败的数据库实际状态，以及 DDL 的提交语义。不能捕获元数据错误后返回空列表，继而推断应当创建或删除对象。

应用用户按最小必要权限运行。SYSTEM 只用于开发环境引导/管理时的必要步骤，验收必须增加非 SYSTEM 应用用户，防止 SQL 只有管理员能执行。所有真实迁移测试使用本次创建的 schema 或明确归属的对象。

## 10 高级能力的取舍与实现边界

### 窗口 frame

完整 ROWS 支持 unbounded/current row/前后 N 行和合法的起止组合。RANGE 明确归入 MySQL/PG 原生窗口能力，检查 peer group、排序列类型和允许的偏移形式。当前 HANA 2.00.088 的 SUM RANGE 实测返回不支持，同一查询使用 ROWS 正常；不再把 RANGE 宣称为三库共同能力，也不能以 ROWS 代替 RANGE。只读验证记录见 DSL 设计第 13 节。

保留已有 row number、rank、lag/lead 等入口。若上游 window 对象没有 frame 挂接点，允许增加薄的窗口规格和函数组合入口，内部复用现有函数及表达式节点；不通过给已有 SQL 字符串追加片段实现。GROUPS、EXCLUDE 等未列入确定范围的语法不自动扩展范围。

### JSON 与 PostgreSQL 数组

普通提取、key 判断、数组索引/长度优先通过 EasyQuery。新增 MySQL JSON 包含和 one/all 路径判断，PG JSONB 包含、key 与路径操作；路径赋值/删除组合进原有表达式更新，分别验证 MySQL JSON_SET/JSON_REMOVE 和 PG jsonb_set/路径删除。JSON 文档值和普通 SQL 字符串必须可明确区分。HANA 不伪装成拥有其他数据库的 JSON 原生修改操作。

HANA 2.0 的数组长度通过显式部署的 SQLScript 标量函数承接既有通用 API，原因是原生 `JSON_TABLE` 无法直接关联外层表别名。函数使用原生 JSON 解析器和调用者权限；部署 SQL 由库提供，应用显式执行并配置 schema。它不引入客户端解析或逐行网络往返，也不会在查询期间自动建库。该部署要求属于支持契约，必须随非管理员验收和迁移说明交付；其他 JSON 提取能力不依赖此函数。

PG SQL 数组支持 String、Integer、Long、BigDecimal、Boolean、UUID、LocalDate、LocalDateTime 的一维绑定/读取，以及 ANY/包含/重叠/长度。`byte[]` 的二进制含义不自动改成 SQL 数组；多维数组不隐式展平。SQL 数组和 JSON 数组不能共用一个会掩盖语义的 API。

共享名称只在输入、NULL、数组和比较语义足够一致时使用。否则保留 `MySqlDsl`、`PgSqlDsl` 的明确边界。JSON path 使用结构化参数和受控渲染，验证引号、反斜线、特殊 key 和非法路径。[MySQL JSON](https://dev.mysql.com/doc/refman/8.4/en/json-search-functions.html)；[PostgreSQL JSON](https://www.postgresql.org/docs/17/functions-json.html)

### 全文检索

三库都提供可用于过滤、投影和排序的有类型入口，但各自的解析模式、索引要求、语言、词法和评分保持显式。HANA fuzzy 阈值和 SCORE、MySQL natural/boolean mode、PG query/vector/rank 分别验证。

测试创建真实索引，并验证命中/未命中、NULL、特殊字符、参数化和评分与当前查询的关联。提供索引 DDL 示例和前置条件，不把全文检索静默降级成 LIKE，也不承诺三库评分数值一致。

### HANA 层级、计算视图与表函数

邻接树能力优先对接上游树查询可等价的部分；完整测试多根、孤儿、循环、重复节点、深度与兄弟顺序。无法等价的 HANA 原生能力使用专属入口，禁止把所有数据拉到内存后假装数据库已完成递归。

计算视图/表函数查询使用已声明的对象和参数元数据，绑定参数，映射回原有实体/DTO。计算视图覆盖模型声明的标量和多值输入；不能把多值输入简单拼成 SQL。表函数覆盖明确声明的标量输入和结构化结果列，表参数和存储过程 OUT/INOUT 不混入这个查询 API。参数名作为标识符受控处理，参数值不能拼接。查询必须能继续组合外层筛选、排序和分页，并验证空值、缺参、多参和嵌套。

必须准备真实的参数化计算视图 fixture。若现有容器无法创建所需对象，应查官方部署途径并提供可复现 fixture；需要额外授权环境时记为必交付阻塞，不能用表函数测试替代后宣布 H11 完成。

## 13 CI 与运行环境

保留本地快速检查和 GitHub 完整验证的分工。本地优先编译、IDEA 诊断、单个 SQL/类型用例和必要的真实问题复现；完整数据库组合、并发和回归交给 GitHub Actions。

Windows/Linux 使用 JBR 17。MySQL 2 GiB、PG 1 GiB；HANA 12 GiB、4 CPU，均保持明确 swap 限制。HANA CI 是强制任务，不得以手动外部实例任务或 H2 等替代。进一步扩大矩阵时，控制并发与资源，不解除限制来隐藏问题。

CI 应从当前基础检查扩展到 API 编译、完整数据库契约、非管理员用户、消费者工程、迁移和必要性能/稳定性用例。长测可以单独分组按阶段执行，但最终验收要求同一候选 commit 的完整必需集合通过。

网络或镜像拉取问题与产品失败分开记录；只有有证据的基础设施偶发失败可以有界重试。断言失败、结果不一致和 flaky 测试必须修根因，不能重复运行到碰巧变绿。

DebugTools 可用于运行中的函数实现调试。实体签名、APT、类型映射、服务注册或缓存变化需要重新生成或重建 runtime。验收使用不加载热重载 agent 的干净 JVM。

## 15 最终完成条件

以下条件缺一项，都不能宣布完整成熟交付：

1. 第 4 节所有必交付能力均有实现和验收证据，已声明的边界与错误行为也有测试；没有偷偷降级、必需 TODO 或以“稍后支持”代替实现。
2. HANA 的普通业务场景通过本包适配器使用既有 EasyQuery API 完成；三库高级能力可以与其正常组合。
3. 非 SYSTEM 应用用户、事务、批量、并发、精度、NULL、复杂查询、迁移和失败场景通过真实环境验证。
4. 类型安全承诺通过正反编译用例验证；公共 API 经过完整消费示例检查。静态类型和结构参数错误在编译/构造时暴露，依赖实际数据的转换或约束错误保留数据库异常上下文。
5. MySQL、PostgreSQL、HANA 的声明支持范围、实际版本和限制一致，所有暴露能力都能追溯到支持表。
6. 性能和资源验证没有未解释的明显回归、额外 N+1 或泄漏；可复现命令、数据规模与报告齐备。

9. 临时测试资源已清理，开发数据库和用户数据按归属保留；仓库无临时日志、密码或无用研究代码，剩余风险和不纳入内容有明确记录。

## 16 无人值守执行规则

### 范围确认后的自主事项

可以自主在本仓库内实现、重构内部代码、完善测试/文档、选择满足上述契约的局部 API 细节、使用当前工具链、创建归属明确的测试资源、检查官方资料、按需克隆参考源码、修复回归并提交/推送工作分支触发 CI。已获授权的常规事项不逐项再次询问。

常规内部命名、包内职责调整、等价 SQL 翻译和错误修复可以自行决定。公开 API 在原型阶段通过使用样例和编译用例定型；既定目标和实体常规写法不能被悄悄改变。

### 必须说明并停下相关依赖工作的情况

- 需要改变这份完整范围、删减必交付项、引入新的数据库或替换 EasyQuery 的核心模型。
- 公开 SPI 无法实现必需语义，需要修改相邻上游、fork APT/执行器或引入不兼容的公共契约。
- 需要额外账户、授权、不可获得的 HANA 对象/环境，或新增付费资源，且已有授权不足。
- 操作会覆盖用户未提交工作、删除归属不明的数据/卷，或修改不属于本项目的持久环境。
- 所有剩余工作都依赖一个无法通过已授权操作解决的外部阻塞。

停下时必须提供具体证据、影响的能力 ID、已尝试方案和最小决策，不以笼统的“有风险”要求重复确认。可独立推进的工作继续做，但不能在关键项阻塞时宣布项目完成。

### 每个工作单元的循环

读取当前 HEAD/工作区与最新进度 → 核对上游和官方依据 → 先定义可复现契约 → 实现共享根因 → 本地针对性检查 → 提交可审查变更 → 必要时推送 CI → 验证对应 SHA 的结果 → 更新任务状态和证据。

整理与功能改动尽量分开提交。测试失败时先保留诊断，定位后再清理。研究 checkout 按用途和 SHA 记录，不提交整个第三方仓库；有用案例先进入正式测试再删除临时产物。

进度记录至少包含：能力 ID、状态、依赖、决定与理由、变更 commit、测试/CI 链接、遗留阻塞及下一步。恢复执行时先检查现场，保留用户新增改动，不能盲目重做已完成工作。

状态只允许事实驱动：计划中、进行中、待验证、通过、阻塞。必交付项不能靠改状态为“不需要”消失。遇到文档或实现冲突，先保持工作区和数据安全，解决冲突后继续。
